# Registre des bugs du legacy

Généré par `retro-verify/scripts/build-legacy-bugs.py` depuis `legacy-bugs.json` — ne pas éditer à la main : les décisions s'enregistrent avec `--decide "BUG-NNN=<décision>"`, le comportement attendu fixé par le métier avec `--expect "BUG-NNN=<texte>"` (marqué « fixé par le métier » ; sinon le SHALL de la règle), la validation d'un SHALL tel quel avec `--confirm-expected BUG-NNN` (ou `all-rule`), le résumé métier et la famille avec `--summary` / `--family` (ou `--annotations`), les décisions exportées depuis le rapport HTML avec `--decisions-file`.

État de l'attendu : **à valider** (SHALL de la règle, pas encore validé), **validé par le métier**, **manquant** (aucun attendu : à rédiger). Un bug « corriger » exige un attendu validé par le métier.

Décisions (gate retro-verify, tranchées par le métier) :

- **Corriger lors de la rénovation** (`corriger`) — la nouvelle application ne reproduit pas ce bug ; ses scénarios sont exclus du golden master, l'exigence est traitée dans le SDD et validée par ses tests.
- **Ne pas corriger lors de la rénovation (bug connu toléré)** (`ne pas corriger`) — le défaut est accepté s'il réapparaît dans la cible ; ni exigence ni test ; ses scénarios sont exclus du golden master.
- **Faux positif — ce n'est pas un bug** (`faux positif`) — ce n'est pas un bug ; la règle est requalifiée `Nature : métier` et ses scénarios restent dans le golden master.
